# 发布更新日志生成

为 gulugulu 生成**面向最终用户**的发布更新日志，套用固定模板。

## 工作流程

### 1. 确定版本号
从 `app/build.gradle.kts` 读取 `versionName`，作为本次版本号（仅用于输出文件名 `release-notes/v{versionName}.txt`，不再写进正文）。如用户在参数里显式指定了版本号，以用户为准。

### 2. 收集更新内容
默认对比**本地领先远程的提交**（即将发布的内容）：

```bash
git fetch
git log --oneline origin/main..main
```

如果用户指定了 tag 区间（如「从 v1.5.2 到现在」），改用 `git log --oneline v1.5.2..main`。
拿到 commit 列表后，按下面规则归纳。

### 3. 归纳规则（开发视角 → 用户视角）
- **去开发术语**：`freeform`、`binder`、`UDF`、`windowingMode`、`smali`、`proxy` 等内部词不出现在更新日志里；换成用户能懂的说法（如「小窗」「后台应用切换」）。
- **保留用户熟悉的梗**：`OHO` / `OHO+` 是用户群熟悉的术语，可保留。
- **合并同类**：多条「优化文案」合并成一条「优化多处文案」；同一功能的多个提交合并成一条。
- **忽略不可感知项**：纯构建 / CI / 版本号 bump / `mapping.txt` 清理 / 无用户可感知变化的重构，不写进更新日志。
- **动词开头分类**：每条用「新增 / 优化 / 修复 / 支持」之类动词开头，简洁一句话。
- **条数**：通常 5~8 条；功能多的大版本可适当多，纯修复的小版本可少。

### 4. 套用模板输出
按下方模板填充「更新内容」：首行固定为「更新内容：」，空一行后开始列条目，**每条之间空一行**。条目编号用 `1.`、`2.` 形式。除条目内容外，格式逐字保留。

### 5. 写入文件并展示
- **写入文件**：保存到 `release-notes/v{版本号}.txt`（纯文本、UTF-8、结尾留一个换行），文件名只用版本号，不带其他前缀。
- **同时在对话里以代码块展示**全文，方便用户直接复制粘贴到酷安 / GitHub Release。
- **覆盖保护**：若 `release-notes/v{版本号}.txt` 已存在，先告知用户并确认后再覆盖，不要静默覆盖。

## 模板

```
更新内容：

1.{更新内容第一条}

2.{更新内容第二条}

...
```

## 参考示例（v1.5.2）

```
更新内容：

1.处理不识别stellar的问题

2.回滚小窗部分代码

3.处理快速启动器图标不显示

4.处理智能截图导致屏幕无法交互

5.处理折叠屏手势错位
```
